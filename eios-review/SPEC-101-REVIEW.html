Governance & Engineering Review

Ready-to-implement plan for EIOS v1.0.1

SPEC-101 describes an ESC-certified emotional-safety engine: a non-bypassable safety router, white-paper-exact metrics, a tamper-evident ledger, and a 100%-branch-coverage pytest suite. This review checks whether the specification itself is complete enough to build and test against — and lays out what to build the moment the base repository is available.

25 findings 9 blocking (critical) 6 modules planned 45 conformance tests specified
Method

Scope & how this review was done

This review reads SPEC-101.md as a contract an implementer, an ESC auditor, and a pytest suite all have to agree on. Every finding below is anchored to specific spec language — a formula, a state-diagram edge, a MoSCoW line — not to a hypothetical implementation choice. Where the six included patches or the one included test (tests/test_auditor_bloom.py) reveal a concrete code shape the spec doesn't fully describe in prose, that's used as corroborating evidence.

No base eios/ repository was provided, so this is a specification and interface review, not a code review. Where a finding has an obvious, low-risk fix, a proposed resolution is included directly in the findings register so implementation isn't blocked on a second round-trip — but every resolution is a proposal for sign-off, not a silent rewrite of the source document.

Findings are organized by severity, then tagged by category (contradiction, undefined variable, unsafe default, incomplete routing transition, ledger-integrity gap, missing consent enforcement, untestable requirement) so they can be triaged the same way the QA Findings Tracker in this organization's own Governance Manual triages Appendix-F items.

Findings Register

25 findings across 7 categories

Ordered by severity. Critical findings block implementation — the router, the core safety metric, or the ledger's core privacy claim cannot be built correctly until they're resolved. High findings should be resolved before the first pytest conformance run. Medium/Low findings can be tracked and closed during implementation.

SR-01CriticalContradiction /
Incomplete routing		 SAFE_MODE is unreachable. The state diagram's only edges are NORMAL→QUARANTINE, NORMAL→CONSENT_GATE, SAFE_MODE→CONTAINMENT, CONTAINMENT→NORMAL, QUARANTINE→CONTAINMENT (“stabilized x N”), CONSENT_GATE→NORMAL. Nothing transitions into SAFE_MODE, yet the Background section explicitly promises recovery “SAFE_MODE → CONTAINMENT → NORMAL.” Insert QUARANTINE→SAFE_MODE on “stabilized x N”, so the full chain reads QUARANTINE→SAFE_MODE→(3 safe turns)→CONTAINMENT→(4 safe turns)→NORMAL.
SR-02CriticalContradiction CIS only fires when route == NORMAL. If a session is already in QUARANTINE, SAFE_MODE, CONTAINMENT, or CONSENT_GATE for an unrelated reason, a trauma-without-consent disclosure in that same turn scores CIS = 1.0 (full integrity) — the exact violation the metric exists to catch is masked by being in any other route. Evaluate the keyword/consent condition independent of current route; reserve the route check (if any) for response-shaping, not for gating whether the violation is scored.
SR-03CriticalUndefined variable ΔI₊ and ΔI₋ are never defined. NAS's formula uses both terms; the spec gives only “ΔI via last turn,” with no rule for splitting a single intensity delta into positive/negative components or whether they're mutually exclusive. Define ΔI₊ = max(0, intensityt − intensityt−1), ΔI₋ = max(0, intensityt−1 − intensityt) — exactly one is non-zero per turn.
SR-04CriticalUndefined variable “intensity” has no declared range. Unlike valence [−1,1] and rumination_score [0,10], intensity (used directly in NAS and EVI) is never bounded — so NAS's max(0, …) floor has no matching ceiling and the metric's output range is unconstrained. Declare intensity ∈ [0,1] in the data model; clamp NAS's final output to [0,1] explicitly.
SR-05CriticalUndefined variable /
Untestable		 REI's entropy term has no binning rule. Shannon entropy requires a probability distribution; “entropy of the last ≤10 intensities” is meaningless over raw continuous samples without a quantization scheme, which the spec never gives. Define a fixed-width histogram (e.g. 5 or 10 bins over [0,1]) converting the last ≤10 intensities into a probability vector before computing H; make the bin count a signed policy-bundle constant.
SR-06CriticalUndefined variable “stabilized x N” leaves N undefined. Every other recovery threshold in the spec is a concrete number (3 safe turns, 4 safe turns); this one — the sole documented exit from QUARANTINE — is not, and “stabilized” itself has no operational test. Reuse the existing “safe turn” primitive (no new trigger, NAS/CIS above a policy threshold) for “stabilized,” and set N = 5 as the policy-bundle default.
SR-07CriticalMissing consent
enforcement		 Consent never expires, is never scoped, and cannot be revoked. It's a single session-level field; once ConsentLevel.EXPLICIT is set it appears to authorize trauma-topic processing for the rest of the session, with no timestamp, scope, or revocation transition anywhere in the model. Add consent_granted_at, consent_scope, and an explicit REVOKE_CONSENT transition that re-arms CONSENT_GATE on the next trauma-adjacent turn — mirroring how this org's own Trust Receipt Workbook scopes consent elsewhere.
SR-08CriticalLedger-integrity gap The Bloom salt is stored in the clear next to the filter it salts. Because the policy-phrase universe is small and fixed, anyone with export access can test every known phrase against a row's Bloom filter using that row's own stored salt — substantially reconstructing which sensitive phrases appeared in raw text. This directly undercuts the ESC Auditor section's “no plaintext” claim. Derive the per-row salt from a keyed function of a secret held only by the auditor/signing process (e.g. HMAC(master_key, session_id ‖ turn_index)) instead of storing it in the exportable row.
SR-09CriticalUndefined variable /
Untestable		 The suicidality-detection trigger is never specified. The single most safety-critical routing rule (“Suicidality → QUARANTINE”) has no defined keyword list, classifier, or threshold anywhere in the document — only the CIS trauma-keyword list surfaces, via a patch, not the spec. Resolve before any other implementation work starts: specify the detection mechanism and its false-negative tolerance in the policy bundle, signed off by whoever owns clinical/safety review.
SR-10HighContradiction PII scrubbing is both optional and already-true. The MoSCoW Requirements section demotes “PII scrubbing” to Should have, while Method/Architecture states as fact that the “Ledger is… PII-scrubbed.” Promote PII scrubbing to Must have (it's load-bearing for the privacy claims elsewhere), or soften the Architecture bullet to describe only what's actually guaranteed (raw text never persisted; hash + Bloom only).
SR-11HighUndefined variable “agency” has no declared range. ΔA = agency − 0.5 is unbounded without one. Declare agency ∈ [0,1] to match the −0.5 recentering, giving ΔA ∈ [−0.5, 0.5].
SR-12HighUndefined variable ConsentLevel is never fully enumerated. Only .EXPLICIT is referenced (via a patch); its other members are never listed in the spec. Enumerate the full set (e.g. NONE, IMPLIED, EXPLICIT, WITHDRAWN) before any consent-path code or tests are written.
SR-13HighUnsafe default Recovery windows are pure turn-counters with no time floor. A user (or an adversarial script) can exit CONTAINMENT by sending a rapid burst of trivial messages, regardless of real elapsed time. Add a policy-configurable minimum wall-clock dwell time per state, required alongside — not instead of — the turn count.
SR-14HighLedger-integrity gap The HMAC chain's threat model is unscoped. A single shared symmetric key both writes and verifies the chain, so it protects against post-hoc external tampering but not against anyone with access to the live key (a compromised or malicious operator) — a distinction “tamper-evident” never draws. State the threat model explicitly (external tamper detection only); if operator-level tamper evidence is actually required, move to WORM storage or a separately-keyed offline-verifiable signature per row.
SR-15HighIncomplete routing CONSENT_GATE has exactly one exit. Only “explicit consent given” leads out; there's no modeled path for refusal, timeout, or continuing in a restricted non-trauma mode, risking a stranded session or a silent, unspecified fallback in the first implementation. Add an explicit CONSENT_GATE→NORMAL (restricted, trauma-depth disabled) transition for a declined or timed-out gate.
SR-16HighIncomplete routing No precedence rule for simultaneous triggers. If a single turn during CONTAINMENT contains both a “safe” signal and a fresh suicidality re-trigger, the spec never says which wins — exactly the kind of ambiguity that becomes a real bypass in the first ad hoc implementation. State an explicit priority order (QUARANTINE-class triggers always evaluated first and override any recovery-counter increment) as a named rule.
SR-17HighUntestable requirement “Non-bypassable” is asserted, not enforced. The property is claimed but never given a structural definition (e.g. a type-level guarantee that Responder is only reachable via Router) — as written it's an aspiration, not a testable invariant. Add an architectural test (or a type/interface constraint) that fails if any code path can reach Responder without passing through Router.
SR-18MediumContradiction Signing is Must-have; key management is a later milestone. Signed export is bundled into the Must-have tamper-evident ledger requirement, yet the Milestones list schedules key management (M9) as future work, with no key-rotation or versioning scheme specified now. Either scope v1.0.1's signing claim explicitly to “single fixed key, no rotation” (matching the milestone list), or pull key management forward into Must-have.
SR-19MediumLedger-integrity gap Bloom parameters and target false-positive rate are unspecified. m/k/ngrams are stored per row, implying they can vary, but no FPR target exists anywhere — without one, “the auditor flags inconsistencies” isn't falsifiable, and 100% branch coverage doesn't capture probabilistic correctness. Fix m/k/ngrams as policy-bundle constants sized to a stated FPR target (e.g. ≤0.1%); add property-based tests asserting the empirical FPR stays under that bound.
SR-20MediumLedger-integrity gap No genesis-row rule for the hash chain. The spec never states what prev_hash is for the first row of a new session. Define a fixed genesis value (e.g. 32 zero bytes, or HMAC of session_id alone) and test every session's first row against it.
SR-21MediumMissing consent
enforcement		 No mid-session consent revocation path. Nothing addresses what happens if a user withdraws consent mid-session, or whether prior logged rows get retroactively reflagged. Add a REVOKE_CONSENT event that appends a new row (never mutates history) and re-arms CONSENT_GATE; state explicitly that past rows are never rewritten, consistent with the ledger's own append-only design.
SR-22MediumUntestable requirement full_replay_audit returns prose, not structured findings. The one included test shows a list of free-text strings with severity embedded as a substring (e.g. “CRITICAL” + “route mismatch”) rather than typed findings. Return {code, severity, session_id, turn_index, message} records instead of prose, with a .summary() renderer on top for humans — the same structured-finding pattern this org already uses for its own QA tracking.
SR-23MediumUndefined variable REI's low-history sentinel (“2.0”) is unexplained. When history < 5, REI defaults to a fixed 2.0 with no derivation or stated relationship to the entropy-based branch's range. Document 2.0 as the entropy-branch's midpoint value (H = 0.5 equivalent under “1 + 2H”) or replace it with an explicit low-confidence marker distinct from any real computed value.
SR-24LowUntestable requirement “p95 performance SLOs” has no number. Listed under Should-have with no numeric target anywhere in the document. Give it a figure (e.g. “p95 turn-processing latency ≤150ms on the reference CI runner”) or drop it from Requirements until one exists.
SR-25LowContradiction /
Undefined ordering		 “Metrics Engine is pure,” but CIS reads Router-mutated state. CIS depends on state.route, which the Router changes; the spec never states whether Router runs before or after Metrics within a turn, so it's unspecified whether CIS reflects the pre- or post-transition route for that same turn. State the turn pipeline order explicitly (proposed: Metrics computed on pre-transition state → Router consumes those metrics → transition applies at end of turn) and pin it with an integration test.
Implementation

Source-code implementation plan

Six modules, each incorporating the proposed resolutions above rather than the spec's literal (and in places underspecified) text. Every design decision below that isn't directly stated in SPEC-101 is flagged as proposed.

eios/core/estate.py — data model

Route (5-value enum: NORMAL, SAFE_MODE, CONTAINMENT, QUARANTINE, CONSENT_GATE) with the corrected transition table from SR-01 encoded as data, not scattered conditionals, so the “non-bypassable” property (SR-17) can be checked structurally. ConsentLevel as a full enum (SR-12): NONE, IMPLIED, EXPLICIT, WITHDRAWN. EmotionVector with intensity ∈ [0,1] enforced at construction (SR-04). EState adds consent_granted_at, consent_scope, and per-transition recovery_counters plus a parallel state_entered_at map for the dwell-time floor (SR-07, SR-13).

eios/config/policy.py — the Policy Bundle, made real

The spec's architecture diagram treats the Policy Bundle as an external config box; it needs to be a first-class, versioned, signable module so every numeric or list-shaped decision below is auditable rather than a silent constant buried in code: suicidality and trauma keyword lists kept separate (SR-09); NAS/REI weights; entropy bin count (SR-05); Bloom m/k/ngrams plus target false-positive rate (SR-19); recovery turn-counts and minimum dwell times (SR-06, SR-13).

eios/metrics/engine.py — compute_metrics(state, emotion)

Pure function over an explicit pre-transition snapshot of state (SR-25). Implements NAS with the ΔI₊/ΔI₋ split and output clamp (SR-03, SR-04), ΔA with declared agency bounds (SR-11), REI via fixed-bin histogram entropy (SR-05, SR-23), EVI unchanged, and CIS evaluated independent of current route (SR-02).

eios/router/router.py — Router + Recovery Controller + Keyword Detectors

Consumes this turn's metrics (never recomputes them) to decide the transition, applies the corrected SAFE_MODE path (SR-01), the CONSENT_GATE refusal/timeout exit (SR-15), the explicit trigger-precedence order (SR-16), and the dwell-time-plus-turn-count recovery gate (SR-13). Exposes a single entry point; Responder is constructed only with a token the Router issues, so bypass is a compile-time/type error rather than a convention (SR-17).

eios/core/ledger.py — hash-chained, Bloom-augmented ledger

SQLite (WAL) as specified. Genesis row uses a fixed, documented prev_hash (SR-20). Per-row Bloom salt is derived from a keyed function of a master secret rather than stored in the row (SR-08). Bloom parameters come from the Policy Bundle, not per-row choice (SR-19). Never persists raw user_text — only its hash and Bloom filter (SR-10). Appends (never mutates) a REVOKE_CONSENT row type (SR-21).

eios/tools/esc_auditor.py & export_cli.py

full_replay_audit returns typed findings (SR-22): {code, severity, session_id, turn_index, message}, with a thin string renderer kept for CLI/human output so the one existing test's substring assertions still have something to match against. Export embeds pubkey and fingerprint per the existing patch; the README/spec states the single-key threat model explicitly rather than implying rotation exists (SR-14, SR-18).
